## 0. 一句话

冰箱开门时，装在**门洞上方**的相机只拍门口这一截：手往里伸、往外拿的那一下。关门后离线分析出"放入 / 拿出 · 什么 · 几件"，
更新库存。库存的**起点由用户初始化**（手动输入或拍照），之后靠进出事件增减，靠一键纠错和定期对账保持准确。

## 2. 整体结构

```text
[门磁 GPIO / 画面触发] ─┐
[门洞上方 USB 相机] ────┴─► 采集进程（实时，唯一职责：不丢）
                              环形缓冲 1–2 秒 → 开门落盘：clip.mp4 + 关键帧 + session.json
                                    │ 关门
                                    ▼
                           分析进程（离线，可失败可重试）
                              ① 切动作：门洞截面上的运动段（和类别无关）
                              ② 判方向：截面两侧的光流 → 往里 / 往外
                              ③ 配往返：伸进去一腿 + 拿出来一腿
                              ④ 看手里：每一腿手里有没有东西、是什么（大模型 + 家庭词表）
                              ⑤ 出事件：放入 / 拿出 · 名字 · 数量 · 置信度 · 证据图
                                    │ HTTP
                                    ▼
                           库存后端 smart_fridge_app（FastAPI + SQLite）
                              初始化 · 事件改库存 · 待确认队列 · 纠错 · 对账 · 保质期
                                    │ 同一套网页
                         ┌──────────┴──────────┐
                  手机浏览器（家里 Wi-Fi）   门边小屏（可选，浏览器全屏）
```

**三个进程分开**：采集必须一直在、不能被分析拖垮；分析可以崩、可以重跑（录像还在）；后端是唯一的账本。
它们之间只通过**会话文件夹 + HTTP** 交流，所以 Mac 和 OrangePi 上是同一套代码，换主机就是复制目录。

## 3. 相机：门洞上方

### 3.1 为什么这个位置好

- E01 的正面机位：人一站到冰箱前，背就挡住了冰箱内部和放东西那一下；空开门 3/3 被切出"动作"（人在动）。
- 门洞上方朝下：人的身体大多在画面外，只剩手臂和手；背景（地面、搁板前沿）稳定；进 / 出就是跨过门洞截面的方向，几何上很清楚；
  **拍不到脸**，隐私更好，这一点报告里值得写。
- 这其实回到了 11-04 [PLAN v2](history/PLAN_v2_20261104.md) 的设想（"冰箱顶部前沿朝下看门口"）；E01 的正面位置只是当晚 Mac 能放的地方。现在有数据说明了为什么不能放在正面。

### 3.2 要提前想到的问题

| # | 问题 | 为什么 | 怎么办 |
| --- | --- | --- | --- |
| 1 | **门格在开口外面** | 门打开后，门内侧的四五层门格跟着门转到柜体开口外面；往门格放饮料**不穿过**门洞截面。E01 的关键帧里饮料瓶基本放在门格，真值 27 件里 12 件是瓶装饮料 | 先量占比（E01 人工表加了"放在哪"一列）；机位选能同时看到开口和门内侧的角度，或者给门格单独划一块区域 |
| 2 | 俯视只看到顶部 | 从上往下看瓶子只看到瓶盖，乌龙茶和可乐的瓶盖很像 | 相机朝屋里倾斜 20–30°，让东西靠近时能拍到侧面 |
| 3 | 景深跨度大 | 放最上层时手离镜头很近（大、糊），放最下层时很远（小） | 广角（对角 ≥ 100°）、1080p、≥ 30 fps；冰箱灯够亮，快门可以短 |
| 4 | 门洞截面在画面里是横线 | 装在上方时，门洞截面在画面里变成一条**横线**，进出变成上下运动；现在 `process_session.py` 只算左右方向，`record_sessions.py` 横线模式的重心算错了 | 改代码（小改动，见 §8）；临时办法是把相机转 90° 装，让截面变成竖线 |
| 5 | 曝光 | 冰箱灯一开一关，自动曝光会大幅波动 | OrangePi 上的 Linux 可以用 `v4l2-ctl` 锁曝光（Mac 不行，E01 已证实） |
| 6 | 冷冻抽屉 | 冰箱下面的抽屉不经过上面的门洞 | 本期只管冷藏室，报告里写明是局限 |
| 7 | 安装 | 嵌入式橱柜冰箱，相机要固定在上方柜体边沿，线不能挡门 | 支架自己设计、3D 打印（旧项目做过扫码枪外壳，建模流程现成） |

### 3.3 先试机位，再做支架

> 11-12 更新：E03 不用手机，直接把 UGREEN 相机用胶带临时贴在下面三个位置，每个位置做同一套 10 个动作
> （步骤和动作清单在本机 `fridge_vision/runs/e03_position_20261112/`）。所以下面说的导入手机录像的工具不需要了。
> 每个位置只有 8 次有物品的动作，分不出计数准确率的高低；选机位看几个是非题：门格拍不拍得到、伸手时脸进不进画面、线往里留的画面够不够、人眼能认出几次。

装支架之前花 30 分钟测一下，和 E01 的方法一样：手机用胶带临时固定在 2–3 个候选位置
（A 门洞正上方垂直朝下；B 铰链一侧上角斜向下，同时看开口和门内侧；C 上方稍靠屋里、朝冰箱倾斜），
每个位置录 10 次（里面搁板 5、门格 3、空开门 2）。看录像数"人眼能认出手里东西"的次数，选最好的那个。
要让现有统计脚本直接处理手机录像，需要一个导入工具（`import_clip.py`，待写，见 §8）。

## 4. 触发：什么时候开始录

- **推荐门磁**：一个 3–10 元的干簧管门磁，接 OrangePi 40 针排针（信号 / 3.3V / 地）。归档里的 `camera_system`
  已经用 libgpiod 读过 GPIO 按钮，接法相同，可以照搬。"纯视觉"指识别靠视觉、用户不用动手；一个门磁不违背（[盲审](BLIND_REVIEW.md) 也这么说）。
- **画面兜底**：在门边缘一小块区域看帧差，配合锁定曝光。
- **环形缓冲**：内存里一直保留最近 1–2 秒画面，开门后连同这段一起存，第一次伸手不会被截掉。
- 相机一直开着（不要开门才打开），USB 相机冷启动要 1–2 秒。

## 5. 识别：往哪走、手里有什么

### 5.1 方向
门洞截面两侧划一条带；带里的运动段就是"一次穿越"；用垂直于截面的光流分量判断朝里还是朝外，再把相邻的一进一出配成一次"往返"。
这套逻辑 `process_session.py` 已经有，只差横线方向。

### 5.2 手里有没有东西，决定放入还是拿出

| 伸进去那一腿 | 拿出来那一腿 | 判定 |
| --- | --- | --- |
| 有东西 | 空手 | 放入 |
| 空手 | 有东西 | 拿出 |
| 有 A | 有 B | 放入 A，拿出 B |
| 有 A | 还是 A | 没放进去 / 看一眼又拿回来，不记 |
| 空手 | 空手 | 整理、推了一下，不记 |

做法由简到难：(a) 每一腿取 2–4 张关键帧直接问大模型"手里拿着什么，空手就答空手"；(b) 先用手部检测（MediaPipe Hands 一类，
OrangePi 上能不能装要实测）找到手，只把手附近裁下来给大模型，更便宜、更隐私、通常更准；(c) 研究里的"手—物体接触"检测
（如 100DOH 数据集，Shan 等，CVPR 2020），报告的相关工作里可以提。

### 5.3 认名
- 多模态大模型（通义千问 VL，OpenAI 兼容接口；密钥找老师），提示词里带**家庭词表**。E01 已经攒了 10 个：乌龙茶、蓝莓、可口可乐、梨、苹果、
  萝卜干酸菜、依云矿泉水、香蕉、酸奶、辣椒酱。
- 纠正过的（图，名字）当示例一起发给大模型：**家庭认名记忆**，不用训练模型就能"学会"你家的东西。
- YOLO 只做辅助：E01 召回 2/27，只认出苹果；香蕉在它的 80 类里也没认出来；它看到的"瓶子"九成是台面上的调料瓶。
- 拿不准就进**待确认**，附证据图，不硬猜。

### 5.4 数量
按包装算件（一盒蓝莓 = 1 件）。散装、按个拿的东西（鸡蛋）只记大概，靠纠错和对账修正。

## 6. 库存：起点、增减、纠错、对账

- **初始化**：第一次用时录入冰箱里已有的东西。手动输入（从家庭词表里选）或拍照（每层一张，大模型列清单，人勾选确认）。
  后端已有"拍照录入会话"（多张照片、人工确认后才入库），可以直接拿来用。
- **事件改库存**：放入 = 新批次（日期取事件时间，保质期按类别）；拿出 = 扣数量；同一样东西短时间内先出后进 = "取用后放回"，不改数量。
- **待确认队列**：置信度低的事件要人点一下"对 / 错 / 改"。纠错次数本身就是指标。
- **每周对账**：对照冰箱里实际有的东西核对系统库存，得到**库存对账准确率**。这是对用户最诚实的一个数字，也能发现慢慢累积的错账。
- 后端已知要改的（[盲审](BLIND_REVIEW.md) 指出、已核对，仍有效）：大模型给的名字没真正当商品名用；类别和保质期仍按英文标签；
  事件状态缺 `confirmed / wrong`；证据图的删除约束和定期清理冲突；"拿出"自动扣减先隐藏；类别表按家里的清单重做。

## 7. 主机与界面

### 7.1 OrangePi 4 Pro 够不够
手册 v1.4 §1.4（[archive/reference/](../archive/reference/)）：全志 A733（2×A76 + 6×A55，2.0 GHz）、NPU 3 TOPS、最高 16 GB LPDDR5、
eMMC / M.2 NVMe / TF 卡、Wi-Fi 6、千兆网口、HDMI 2.0、MIPI 屏和 MIPI 相机接口、USB 3.0×1 + 2.0×3、40 针 GPIO、Type-C 5V 3A 供电、Ubuntu / Debian。

**够用**，因为 v4 不要求实时识别：开门期间只录像，关门后花十几秒分析一段 20 秒的录像就行；认名走网络上的大模型。NPU 暂时用不上（工具链成本高）。
（11-08 更新：老师在板子上接入了出厂自带的 NPU YOLOv5s 模型，识别时约 14 帧/秒，现在实时计数用的就是它；自己转换别的模型到 NPU 仍然成本高。）
风险在**装机时间**（系统、OpenCV、相机、GPIO、开机自启，第一次可能要大半天）、TF 卡寿命（录像循环写盘，最好用 eMMC 或 NVMe）、
5V 3A 电源要稳、散热、别放在冰箱顶部出热口上。装机清单见 [deploy/](../deploy/)。

### 7.2 你们提的两个方案

| | A：OrangePi + 门边小屏 | B：OrangePi + 手机 |
| --- | --- | --- |
| 什么时候确认 | 关门那一刻，就在冰箱边，记得最清楚 | 之后掏手机，可能忘 |
| 额外硬件 | 屏幕（官方 10.1 寸 MIPI 屏见手册 §3.29，或任意 HDMI 触摸屏）、支架、走线 | 无 |
| 开发量 | 网页 + 全屏浏览器 + 触屏适配（湿手、大按钮） | 网页 + 手机适配 |
| 家人上手 | 不用装东西，路过就能看 | 要知道网址、加到主屏 |
| 演示和视频 | 很直观 | 也行 |
| 在外面查库存 | 不能 | 只有局域网能用；要远程得另想办法 |

### 7.3 建议：一套网页，两块屏，手机先
- 后端本来就是"给 HDMI 触摸屏和局域网手机用"的（见 `smart_fridge_app/README.md`），所以 A 和 B 是**同一套前端**：
  小屏就是全屏浏览器打开 `http://localhost:8000`；手机打开 `http://<主机名>.local:8000`，再"添加到主屏幕"。
- 顺序：手机先（零硬件，反正要做）；识别链路稳定后再加小屏，它的价值是"关门即确认"和演示。
- **不建议做原生 App**：iOS 上架要开发者账号（每年 99 美元）；微信小程序要公网 HTTPS 域名和备案；网页加到主屏幕已经够用。
- **不要把端口开到公网**（后端没有登录）。以后要在外面查库存，用 Tailscale / ZeroTier 这类组网。提醒推送可以以后再接（微信机器人、Bark、ntfy 等）。
