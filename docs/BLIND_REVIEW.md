# 盲审报告

## 一、独立设计（未看现有方案）

**1. 进出判断。** 不让分类检测器当守门员。开门→整段录像落盘（7 天环形）；门口 ROI 做类别无关的"手持物体穿越"检测（帧差 + 手/人框），每次穿越取 3–5 张关键帧，关门后一次性发给多模态大模型，返回名称、数量、方向、置信度；方向用轨迹粗判、大模型复核。理由：家用冰箱是长尾（袋装菜、盒装剩菜、酱料瓶），80 类检测器没认出来就静默漏掉；大模型每天几十次调用成本可忽略。实时不是需求，关门后 10 秒出结果足够。

**2. 数据：4 张表。** sessions（开关门时刻、片段路径）；events（session_id、方向、名称、数量、置信度、关键帧、状态 auto/confirmed/wrong、修正后名称）；items（名称、类别、默认保质天数、别名）；lots（item_id、数量、入库日、到期日、来源 event_id、状态）。库存由 lots 派生。

**3. 手机端最重要的一屏：** 按开门会话分组的事件流，每条带图和系统判断，一键"对 / 错 / 改"。库存清单是派生品；信任靠这一屏建立，"每天纠错次数"这个指标也要求用户看每一条。

**4. 先验证的假设：** "门口单摄像头在真实光线、真实动作下，能把 ≥80% 放入动作拍成大模型可命名的画面。"做法：有线相机装上真冰箱，不跑识别，录 3 天真实开关门，人工标每次放了什么；关键帧给大模型，统计可见率、命名正确率、亮度触发漏/误。3–4 天，写代码前做。

**5. 五周能到的程度：** 开门自动捕获、放入物品自动命名入库、手机审核、库存/临期、连续用两周——能。可靠的"拿出"记账、数量（一手三个鸡蛋）、袋/盒内物品、手握住的小件、两人同时操作——不能。每天开门 10–20 次时，"纠错 ≤2 次/天"要求事件级准确率 85% 以上，达不到；现实是 20–30% 的事件要改。

## 二、现有方案与挑错

**三处最大差别**

1. 守门员。现有方案用 YOLO（80 类或 COCO）当触发器，大模型只在轨迹过线后复核（door_demo.py 306–340）。检测不到 = 没轨迹 = 没事件 = 没关键帧，漏记不可见。我的是类别无关穿越 + 大模型认名，更合理：用户要的是"放了什么"，不是"过了几个已知类"。
2. 逐帧实时过线 vs 关门后离线分析。现有方案为 T5"≤3 秒入账"逐帧跑检测 + 追踪，min_age=3、1.5 秒去重都在修补逐帧判定的抖动（LineCounter 102–150）。没人需要 3 秒；离线可看整段、可重试，更合理。
3. 无审核状态的自动记账。status 只有 applied/unmatched/undone（004 迁移第 40 行），没有"已确认/判错"字段，准确率永远测不出来；唯一的反馈界面（首页卡片）至今未做。审核状态必须进 schema。

**被锚定的地方**

- shelf_life.py 10–32 行：类别集合就是那个 80 类数据集的类名（mangoteen、jalepeno、stilton cheese），豆腐、袋装菜、剩菜、酱料都不在，而"家里常买 20–40 种"清单在 PROPOSAL §12 仍未决。保质期表建在了错误的类目上。
- PLAN"怎么数"一行"和人流计数同一套成熟方法"——人流计数成立靠 person 类检测可靠，这里对象恰恰检测不可靠。
- "纯视觉"被扩展成"开门检测也必须纯视觉"（PLAN 关键决定首行；door_demo.py DoorDetector 41–81）。用户的"纯视觉"是"不要我动手"，3 元门磁不违反。两个具体问题：基线只在关门态更新（66–73），厨房灯一开"开门"就锁死到灯灭；没锁自动曝光，USB 相机 1 秒内把亮度拉回基线即触发"关门"（75–78），会话丢失。
- "视频不落盘"（PROPOSAL §3 设计原则）是产品期隐私原则，研发期用它等于自废武功：漏检无录像可查；微调集只含 YOLO 已认出的东西（PLAN 4.1、M4），修不了漏检。
- "自动记账 + 事后撤销""拿出要不要记"在 PLAN 末尾仍"待确认"，但 schema 和 consume 逻辑（door_events.py 209–249）已写死。
- "大模型管认名"没落地：door_demo.py 168–185 只把 vlm.count 写进 payload，label_zh 仍是 YOLO 的，record() 130–133 用它建商品；除非路由层替换（未读），大模型的名字只躺在 vlm_json。correct()（336–353）同病：改名后 category 和保质期仍按原英文 label 算（133、180），"wine glass"改"牛奶"仍是饮品 14 天。media_id ON DELETE RESTRICT 与 §11"90 天清理证据图"冲突。

**砍 / 加 / 先改**

砍：M4 微调（数据有偏，4 天不够）、"拿出"路径先隐藏、按 80 类建的保质期表。加：开门片段落盘、类别无关穿越触发 + 大模型全帧命名、events 的 confirmed/wrong 字段与事件流页面、每日真值记录。先改：相机装到真冰箱录 3 天、不接识别、手标真值——这决定架构，而它还没发生（acceptance.md 只有桌面 FaceTime + COCO 杯子 9/9）。

**时间与准确率估计**

偏乐观：M2 12 天内真实差分 ≥70%（相机几何、触发、召回三个未知叠加）；M4 4 天完成标注 + 微调 + mAP50≥0.7 + 20 种 85%（200 张/30 类≈7 张每类，验证集还是同批）；T13 后 7 天 ≤2 次/天；T4 亮度法 20 次零漏零误。偏保守或无意义：M1 ≥8/10（桌面 COCO 物体，说明不了问题）；M3 3 天可行；N100 15–25 fps 大致合理。

**最该警惕的盲点**

只测"系统报出来的"，不测"实际发生的"。所有验收都是"摆一个检测器已认识的动作、数命中"，真实家庭的漏检因视频不落盘而不可见。一人 + 一 AI 助手尤其危险：AI 能源源不断产出通过的测试和绿勾（34 个测试、9/9），而真正的指标——真实放入动作被正确记录的比例——没有任何测量路径。

## 三、结论

值得继续；接下来 7 天唯一的事：相机装上真冰箱，录 3 天真实开关门，人工标出每次放入了什么，统计可见率 / YOLO 召回 / 大模型命名正确率——在这个数字出来之前，一行识别代码都不要再写。
