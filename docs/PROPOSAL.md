## 1. 项目一句话

在冰箱门口装一个摄像头，开门时自动记录放进去、拿出来的食材，不用扫码、不用拍照；并且能**用数字说明自己有多准**。

**为什么值得做**。家里冰箱放了什么没人记得清，剩菜过期、重复买是常事。前身项目"饮食均衡助手"做了手机拍照识别和扫码枪，技术上能用，但要用户多做一步，于是没人用。所以这一期把交互压到零：开门即记账，认错了在手机上一键纠正。

## 2. 这个项目对申请意味着什么

招生官和老师看的不是"做了一个 AI 产品"，而是一个中学生能不能：发现真实问题 → 提出假设 → 动手测量 → 发现假设错了 → 改方案 → 再测 → 写清楚学到什么。这个项目的故事线正好是这样，而且每一步都真实发生、有记录：

1. **起点**（更早）：手机拍照识别 + 扫码枪，能用但没人用。教训：多一步就不用。
2. **转向**（11-04）：零交互、纯视觉、开门触发，追手里的东西。
3. **第一版**（11-04～06）：80 类食物检测器 + 追踪 + 虚拟线过线，桌面测试 9/9，看起来很好；一个 Tims 杯子被认成"wine glass"是第一个信号。
4. **质疑**（11-07）：你问"你的设计够不够中立"。请了一个没有上下文的独立审阅挑错，结论：所有验收都在测"系统报出来的"，没测"实际发生的"；守门员认不出的东西会静默漏掉。
5. **测量优先**（11-07 起）：相机装上真冰箱，录真实开关门，手记真值，算触发可靠性、可见率、YOLO 召回、大模型认名正确率。
6. **用数据定架构**（11-08），**做一次有前后对比的改进**（11-21/22），**连续真实使用并记每天纠错次数**（11-16 起）。

**要做好的难点**（而不是做全）：在真实厨房的光线和动作下，可靠地把"什么东西、往哪个方向过了门口"捕捉下来，并且能度量自己的准确率。认名交给大模型，库存后端是现成的，这两样不是重点，也不必假装是。

**三句能讲的话**（报告、文书、面试共用）：我先测量再动手；我为长尾设计，不靠固定类别表；我把人放进回路，用"每天纠错次数"衡量系统。

**诚实边界**。代码有 AI 助手参与，硬件和指导有老师参与。日志、提交记录和报告里的"协作说明"一节写清楚哪些是你做的、哪些是帮的；你必须能解释报告里每一个数字是怎么来的。这比"全是我一个人做的"更可信。

## 3. 系统设计（3.0 方向，11-08 用数据拍板）

```text
门口相机（临时：有线 1080p 定焦；正式：Moertek 2.4G）
   │
   ▼
开门检测：画面亮度跳变（可手动 o 兜底；触发不可靠则加门磁）
   │ 开门
   ▼
研发期：整段录像落盘 runs/sessions/<id>/clip.mp4 + 过线关键帧 + session.json
   │ 关门
   ▼
离线分析（关门后几秒内，不要求实时）
   ├─ 类别无关过线：门口竖带的帧差"爆发" → 一次穿越；光流方向 → 朝冰箱 / 离开冰箱
   ├─ 配对成"一次伸手"：进去一腿、出来一腿；哪一腿手里有东西决定 放入 / 拿出
   ├─ 认名：关键帧整帧交给多模态大模型（可选 YOLO 辅助）；会话内多帧投票
   └─ 事件：放入/拿出 · 名字 · 数量 · 置信度 · 证据图
   │
   ▼
库存后端 smart_fridge_app（现成：商品 · 批次 · 流水 · 撤销 · 备份，34 个测试）
   │
   ▼
手机网页（家里局域网）："刚才的变化"按会话分组，每条带图，一键 对 / 错 / 改
   │ 纠错
   ├─ 每天纠错次数（使用期指标）
   ├─ 家庭认名记忆：纠正过的 (图, 名字) 做示例喂给大模型，下次认得
   └─ 回放评测集：同一批录像上重跑新算法，前后对比
```

**和 2.2 的三处不同**：守门员从"80 类检测器"换成"任何东西过线都算"；从逐帧实时换成关门后离线，可以看整段、可以重试；记账多了"已确认 / 判错"状态和纠错页面，准确率才测得出来。原来的 `door_demo.py`（检测 + 追踪 + 实时过线）保留为对照组，11-08 看数据决定去留。

**设计原则**

- 没有数字不改架构；每个改动都在同一批录像上前后对比。
- 为长尾设计：家里常买的东西不在任何类别表里，名字由大模型给、由人纠正。
- 人在回路：自动记账 + 一键纠错，纠错本身就是数据。
- 隐私分级：研发期录像留在 Mac 本地；产品期只留关键帧并定期清理；对外展示只用无人脸的帧。
- 同一套代码：Mac 上做完，换主机只是复制目录。

## 4. 评测方法（本版核心）

真值协议：录制脚本在每次关门后在终端里问"放入了什么 / 拿出了什么"，照实打；什么都没拿也要记（直接回车），它是误动作的负样本；刻意补的"练习轮"备注写"练习"。`runs/sessions/` 是私有评测集，不进 GitHub。

| 指标 | 定义 | 工具 | 决定什么 |
| --- | --- | --- | --- |
| 触发可靠性 | 可疑误触发（< 2 秒的会话）、超时强制关门（疑似厨房灯）、漏触发（人工记） | `analyze_sessions.py` | 亮度法够不够，要不要门磁 |
| 可见率 | 有"放入"真值的会话里，拍到至少 1 张关键帧的比例 | `analyze_sessions.py` | 相机位置、角度、线位 |
| YOLO 召回 | 真值物品被 YOLO 在该会话里看到过的比例 | `analyze_sessions.py` | YOLO 能不能当守门员 |
| 认名召回 / 精确率 | 真值物品被大模型叫出来过的比例；大模型给的名字对得上真值的比例；失败按 看不清 / 遮挡 / 不在画面 / 认错 分类 | `name_keyframes.py` | 大模型认名可不可靠，失败主因是什么 |
| 动作检出 / 次数一致 / 方向一致 | 有真值的会话里检出 ≥ 1 次伸手的比例；伸手次数等于真值件数的比例；单向会话里方向全对的比例；空开门却有动作的会话数 | `process_session.py`（11-07 晚在写） | 类别无关过线 + 光流方向这条路行不行 |
| 每天纠错次数 | 真实使用期，家人每天在手机上点"错 / 改"的次数 | 后端统计（11-14 起） | 系统到底好不好用；改进前后对比 |

目标不是一次达标，而是每个数字都有来源、有趋势。盲审对 2.2 的批评正是"没有任何一条测量路径"；本版把测量放在写识别代码之前。

## 6. 新构思（本版新增，按性价比排序）

1. **家庭认名记忆**。每次你在手机上纠正一个名字，就把 (证据图, 正确名字) 存起来；下次调大模型时把最近的几个例子一起发过去："在这个家，这种红杯子叫 Tims 咖啡"。不用微调就能"学会"你家的东西，而且效果可以用认名精确率的前后对比来证明。这是最适合写进报告的改进。
2. **会话级投票**。一次开门有多张关键帧，大模型逐帧认名后按置信度加权投票，比单帧稳。`name_keyframes.py` 已输出逐帧结果，投票在 `process_session.py` 里做。
3. **门磁兜底**。如果今晚的触发可靠性差（厨房灯误触发多、漏触发多），用一个几块钱的门磁 + ESP32/Arduino 走串口报"开 / 关"。机构有硬件和老师，一个下午能做；"纯视觉"指的是不要用户动手，不是禁止一个传感器。
4. **回放评测**。所有录像落盘，任何算法改动都在同一批会话上重跑，出一张"改动前 / 后"表。这是让"我改进了"变成可证明的句子的唯一办法。
5. **失败图集**。每类失败（看不清、遮挡、不在画面、认错、误触发）各挑一张图，配一句原因。报告和面试最有说服力的素材。
6. **隐私分级**（见 §3 原则）。大模型只收关键帧，不收整段录像；可以说明将来换成本地小视觉语言模型的路径。
7. **食物浪费统计**（可选，11-28/29）。按批次统计"到期未用"的次数，把项目的意义从"记账"提到"减少浪费"。
